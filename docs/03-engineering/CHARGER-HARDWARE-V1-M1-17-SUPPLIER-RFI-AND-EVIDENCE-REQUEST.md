# M1.17 — Supplier RFI and evidence request package

**Status:** DRAFT — ready for controlled supplier review; not sent.  
**Date:** 2026-11-11  
**Scope:** Phoenix Contact CHARX control modular cluster and EMH iML e-moc metering/OCMF integration.  
**Decision boundary:** information request only. No component approval, purchase, wiring release, energisation, billing approval or production release.

## 1. Purpose

Convert the unresolved M1.1–M1.16 assumptions into written, revision-controlled manufacturer answers. Request exact documents and explicit confirmation for the proposed four-output prototype:

- 1 × CHARX SEC-3xxx cluster controller (variant to be confirmed) + 3 × SEC-1000 point controllers, using the manufacturer-approved DIN-rail backplane.
- Four separately attributable EMH iML e-moc meters, one per charging point, on the supported RS-485/Modbus/OCMF architecture.
- Optional, separate grid-infeed meter only where required for load management.
- Each output retains its own local EVSE safety chain; no gateway, cloud, payment or shared meter may replace per-output protective functions.

This is a supplier RFI, not an instruction to disclose confidential design data. Supplier may provide secure document links or identify the appropriate technical/commercial contact.

## 2. Request handling and response rules

For every answer, request:
1. Exact product order code, hardware revision and firmware version.
2. Document title, document number, revision/date and page/section.
3. Whether the answer is **supported**, **supported with conditions**, **not supported**, or **not confirmed**.
4. Any required accessory, licence, configuration tool, certificate, service or recurring fee.
5. Product lifecycle status, replacement code, lead time and warranty.
6. Written identification of any assumptions or exclusions.

Do not convert verbal guidance, generic family brochures, third-party reseller listings or a similar product variant into approval evidence. Preserve unanswered items as OPEN. Attach supplier replies and referenced documents to the project evidence register before changing any selection gate.

## 3. RFI-A — Phoenix Contact

**Subject:** Technical confirmation request — CHARX control modular four-point AC EVSE, EMH iML e-moc / OCMF metering

### A1. Exact topology and compatibility

Please confirm whether the proposed topology is supported as a single cluster:
- one exact SEC-3xxx order code (please state the recommended variant);
- three SEC-1000 modules;
- four independent charging points;
- four EMH iML e-moc meters, each uniquely assigned to its corresponding charging point.

Please provide the supported maximum module count, exact backplane/connector accessory order codes, mechanical assembly instructions and the complete compatibility matrix for the stated firmware. Confirm whether the proposed four-meter arrangement is supported concurrently, not merely whether each meter appears individually in a compatibility list.

### A2. Firmware and OCMF

The project evidence currently identifies CHARX help for firmware 1.9.1 and an OCMF/legal-metrology listing for EMH iML e-moc at firmware 1.09 / OCMF 1.4.1. Please confirm:
- exact CHARX firmware build and SEC-3xxx/SEC-1000 combinations required;
- exact supported EMH iML e-moc hardware/firmware variants;
- OCMF version, profile/options and any firmware licence;
- whether four simultaneous sessions can each produce independent, correctly attributed OCMF records;
- whether signed records are generated by the meter, controller or another component, and which signature/certificate validation chain is supported;
- whether OCMF records are accepted by the intended CHARX OCPP backend path, including any server-side prerequisites.

Please provide the current official compatibility table and release notes. A statement that a meter supports OCMF in isolation is not sufficient to establish the complete CHARX integration.

### A3. RS-485 / Modbus physical and logical interface

Provide the exact supported wiring diagram and terminal schedule for:
- meter bus connection(s), polarity and reference;
- bus topology, termination and biasing;
- galvanic isolation and permitted common reference;
- cable type, maximum length, shielding and shield termination;
- baud rate, parity, stop bits, slave address range and address assignment;
- polling interval, response timeout, retry policy and bus recovery;
- whether one bus can host all four meters, or separate ports/buses are required;
- supported meter register/profile mapping and configuration import/export.

Do not infer terminal numbers from functional connector labels. State exact terminal designations from the applicable hardware revision.

### A4. Offline persistence and recovery

For a public charging deployment, describe the supported behaviour when WAN, backend, OCPP session, cluster gateway, RS-485 bus, meter or controller supply is interrupted:
- which component persists transaction and signed meter records;
- record capacity and retention policy, including a quantified minimum or documented limit;
- atomicity and duplicate prevention;
- behaviour on abrupt power loss during an active session or record write;
- restart/reconnection reconciliation and ordering;
- clock source, time synchronisation and timestamp integrity;
- export/retrieval procedure if backend synchronisation fails;
- behaviour on storage full, corrupted record, invalid signature or missing meter data;
- whether local authorisation and charging continue, and under which explicitly configurable policy.

Please distinguish documented product behaviour from behaviour that requires a custom application/backend. Do not assume that generic “offline event actions” proves durable OCMF transaction retention.

### A5. Safety and output independence

Confirm the exact supported local safety/control allocation for four points and identify shared failure dependencies. Specifically:
- What happens to each output if SEC-3xxx stops, reboots or loses power?
- What happens if the DIN-rail bus is interrupted between modules?
- Can unaffected SEC-1000 outputs continue in a defined safe mode?
- Which faults force one point off versus the complete cluster off?
- How are contactor command, feedback and welded-contact detection handled?
- Which exact contactor coil loads, inrush and suppression networks are supported by the output?
- Which RCM sensor models, wiring and firmware functions are validated?
- What external RCD/protective coordination is required by the manufacturer?
- What watchdog, safety-related diagnostic and restart interlocks are provided?

Request a failure-mode table and relevant safety documentation. Do not describe the cluster as four autonomous EVSEs unless Phoenix explicitly supports that claim with conditions and evidence.

### A6. Power budget and peripherals

Confirm:
- maximum permitted backplane load and its measurement boundary;
- whether the published 6 A nominal backplane limit applies to this exact cluster;
- measured/declared consumption per SEC-3xxx, SEC-1000 and each supported peripheral;
- approved power supply order code(s), input range, protection and redundancy requirements;
- whether RFID/NFC PCB 1391227, EV-RCM-6DC-WAT 1309697 and cable 1360462 are supported in the stated cluster;
- whether one RFID reader may serve four outputs, or one reader per output is required;
- whether any supported 12 V distribution is permitted over the backplane (do not assume it is);
- approved load and inrush budget for locks, contactors, sensors and indicators.

Please identify any peripheral combinations that exceed the available current or are mutually exclusive.

### A7. Lifecycle, security and support

Provide current lifecycle status and replacement roadmap for all proposed order codes; security advisories and firmware update policy; signed firmware/update mechanisms; vulnerability reporting channel; configuration backup/restore; access-control model; support period; warranty; lead time; MOQ; and EU/Portugal technical support route.

## 4. RFI-B — EMH Metering

**Subject:** Technical and legal-metrology evidence request — iML e-moc for four-point AC charging

### B1. Exact product and certificates

Confirm exact iML e-moc order code, hardware revision, firmware, current lifecycle status and availability. Supply:
- complete current datasheet and installation/operating manual;
- EU declaration of conformity;
- exact MID certificate and annexes, including instrument category, accuracy class, measurement modes and certificate scope;
- applicable national type approvals or national legal-metrology evidence;
- applicable conformity assessment module and notified body details;
- any restrictions on use for public EV charging, resale of electricity or customer billing;
- sealing, access protection and tamper-event documentation.

State clearly what the certificates do and do not cover. A general “MID approved” statement is insufficient without the exact certificate and scope.

### B2. Electrical and thermal limits

Confirm direct connection suitability for the project reference of 3-phase 400 V and 32 A continuous per output:
- rated/current range and permissible continuous operation at 32 A;
- overload and short-duration limits;
- terminal conductor range, material, temperature class, tightening torque and strip length;
- thermal dissipation and required enclosure/spacing/ventilation;
- upstream/downstream protection requirements and conditional short-circuit rating;
- installation category, pollution degree, insulation and overvoltage category;
- whether four meters in one enclosure require derating or spacing.

Confirm the auxiliary 12 V supply requirements, peak/inrush current, isolation and behaviour on loss/recovery of auxiliary supply. Do not treat the published nominal current range alone as proof of continuous thermal suitability.

### B3. OCMF, signature and communications

Confirm the exact OCMF version/profile supported by the meter and CHARX firmware 1.09 integration:
- signed record format and signature algorithm;
- key generation, provisioning, storage, rotation and revocation;
- certificate chain and verification method;
- monotonic counter/sequence and replay/duplicate handling;
- timestamp source and clock-loss behaviour;
- Modbus RTU register map, data types, scaling, byte/word order and error codes;
- OCMF record retrieval, acknowledgement and deletion semantics;
- record capacity, retention and overwrite behaviour;
- concurrent independent operation of four meters;
- behaviour on bus failure, meter reset, power loss and full storage.

Please provide protocol specifications and example test records/signatures, with any sensitive material redacted.

### B4. Measurement boundary and installation

Provide the manufacturer-approved measurement connection diagram for a charging point, including the relationship between meter, contactor, protective devices and connector. Identify any restrictions on conductor routing, neutral, directionality, auxiliary supply and sealing. The project will not place the meter relative to the contactor or define terminal wiring until this diagram and the certified measuring boundary are reviewed.

### B5. Commercial and lifecycle

Provide current order code, EU stock/lead time, MOQ, indicative pricing, warranty, calibration/verification requirements, service/replacement process, firmware support period and end-of-life notice process.

## 5. RFI-C — Independent Portugal review (IPQ / qualified legal-metrology adviser)

This is a separate review and must not be answered by assuming manufacturer MID documentation alone settles Portuguese legal use.

Request written guidance for the exact proposed meter and intended business model:
1. Is the exact meter certificate and conformity-assessment scope sufficient for the intended measurement and customer-billing use in Portugal?
2. Are national additional approvals, first verification, periodic verification, in-service controls, seals or approved installation conditions required?
3. Which entity is competent for each approval/verification step, and what evidence must the operator retain?
4. Does the proposed direct meter installation and OCMF signed-record chain satisfy the applicable requirements, or are additional controls required?
5. Are requirements different for private fleet, workplace/shared private access and publicly accessible charging?
6. What changes if the operator charges by kWh, time, session or a combination?
7. What transition or maintenance obligations apply if the meter, firmware, enclosure or measurement circuit is changed?

Record the adviser’s identity, competence, date, scope and cited legal provisions. This request is not a legal opinion and does not claim IPQ has reviewed the design.

## 6. RFI-D — Operator, payment and fiscal workflow review

Obtain qualified Portuguese advice for the selected operating model:
- public versus private access classification;
- AFIR ad-hoc payment and price-display obligations for a 22 kW public point;
- payment terminal / secure internet payment / QR route conditions;
- invoicing, VAT, fiscal device/software and transaction evidence;
- refunds, disputes, chargebacks and interrupted-session settlement;
- treatment of meter/OCMF record as evidence in disputes;
- GDPR roles, lawful basis, data minimisation, retention, access and deletion;
- offline authorisation limits and reconciliation;
- consumer information, support and accessibility.

Payment and commercial software remain outside the local EVSE safety chain. No payment provider, fiscal integration or tariff is selected by this RFI.

## 8. Acceptance criteria before design freeze

The meter/controller architecture may advance beyond prototype only when all applicable criteria are met:

- Exact order codes and hardware/firmware revisions are frozen with current manufacturer documentation.
- Phoenix confirms the four-output topology and four concurrent per-point meter integrations in writing.
- Exact terminal schedule, bus topology, power budget and approved PSU are available.
- EMH supplies certificates and evidence covering the intended measurement/billing use; Portuguese legal-metrology review is documented.
- OCMF signatures are independently verifiable and four outputs remain correctly attributable under concurrent operation.
- Offline transaction retention, power-loss behaviour, recovery, duplicate handling and storage limits pass witnessed tests.
- Each output's local safety chain and shared-cluster failure responses pass the approved bench plan.
- Thermal, protective coordination, enclosure, wiring and installation are reviewed by qualified professionals.
- AFIR, fiscal, payment, consumer and GDPR operating model is reviewed for the actual deployment type.

Any unsupported or ambiguous item remains OPEN and blocks the relevant release gate.
